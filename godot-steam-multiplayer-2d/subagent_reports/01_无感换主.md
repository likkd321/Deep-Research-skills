I wrote the JSON for Seamless_Host_Migration_D3_D4 to `/home/user/Deep-Research-skills/godot-steam-multiplayer-2d/results/Seamless_Host_Migration_D3_D4.json`. **Bottom line:**
- **Can it be truly seamless on pure Steam P2P? Only with a big rewrite.** Godot's built-in multiplayer API with SteamMultiplayerPeer cannot do it. The best you get there is a pause-and-restore handover of a few seconds (the separate D2 item).
- **Why not:** the host is always peer ID 1, and Godot has no API to hand that ID to someone else. When the host leaves, clients get `server_disconnected`, and the objects that MultiplayerSpawner/MultiplayerSynchronizer manage disappear. The engine proposal for this (godot-proposals#7912) has been open since September 2023 with no maintainer reply.
- **What does work:** dropping Godot's multiplayer API and sending messages directly through GodotSteam's Steam Networking Sockets/Messages. Each player keeps open connections to the host and the next two in line. The game rules must also be rewritten as pure logic that can be saved and loaded as bytes. Understudy shows this can work, but only in tests on one machine.

**Is "Godot Understudy" real? Yes, but it is very new.**
- It is on the Godot Asset Store (author ags221) and archived on Zenodo. Version 0.1.0 was released 2026-10-07/08, is marked unstable, and had 0 reviews when I checked.
- It is pure GDScript for Godot 4.5 and later (4.3 and 4.4 are not supported), and free under CC0/MIT-0. The store page says Claude wrote the code under the author's direction.
- I downloaded the source and read the architecture, lessons and Steam transport files. The design is a host, a "shadow" that runs a live copy and takes over after 170 ms of host silence plus a majority vote, and a "standby" with a once-per-second copy.
- It sends all traffic through Steam's relays (SDR) with direct connections turned off, so player IPs stay hidden.
- All of these figures are the author's own, from one Linux machine:

| Test | Players | Gap between hosts |
|---|---|---|
| Repeated host crashes | 8 | median 228 ms, max 262 ms |
| Over real Steam relays | 4 | max 235 ms |

- With 8 players the host uploads about 700 kbit/s and each player about 47 kbit/s.
- It has never been tested between players on different networks. The author's lessons file lists more than 40 timing and voting bugs, which shows how hard writing this from scratch would be.

**Photon Fusion:**
- The Unity version (Fusion 2) does have host migration, but it is the pause-and-restore kind, not seamless. Saved snapshots (about 30 s apart recommended) can lose recent changes, and every player reconnects.
- The Godot version (Fusion 3) is a preview, and Photon says not to use it in production (build 684, 2026-10-26, Godot 4.6+). Its state is kept on Photon's cloud, so objects owned by the master client move automatically when the master leaves. It depends on Photon's cloud, not just Steam.
- **Cost:** 100 concurrent users free. From a third-party summary, not confirmed with Photon: about $125/month for 500 concurrent users, $250 for 1,000 and $500 for 2,000.

**Among Us style:** the official server forwards all game data. When a player leaves, the server announces the new host's ID and the match continues. On Steam, the lobby's automatic owner transfer could do the electing, with messages sent to every lobby member. You would need your own heartbeat checks, because Steam may take seconds to notice a crashed owner; I could not confirm how long.

**Verdicts for the eight "seamless" cells** (win rates for a solo developer working with Claude are my own estimates):

| Mode | Timing | 4-6 players | 7-12 players |
|---|---|---|---|
| PVE | Frame-insensitive | Feasible, ~50-60% | Feasible to marginal, ~40-50% |
| PVE | Frame-sensitive | Marginal, Understudy only, ~25-35% | Marginal to not advised, ~15-25% |
| PVP | Frame-sensitive | Not advised, ~10-20% | Not advised, under 10% |
| PVP | Frame-insensitive | Feasible with lockstep or turn-based, ~45-55% | Marginal, ~35-45% |

For frame-insensitive games, the simple route is every client keeping a full copy of the game state plus Steam-lobby election, or lockstep where only the input-relaying coordinator changes. A 0.3-1 s stall there is effectively unnoticeable.

**Other ratings:**
- Overall difficulty 4.5/5.
- How likely Claude writes it correctly, overall 2/5:
  - Using Understudy: 3/5, but Claude must be given its source because the library is not in its training data.
  - Writing the shadow-copy design from scratch: 1.5/5.
- Cost is $0 on the Steam-only route.
- Main sources: the Understudy store and Zenodo pages, Photon's Fusion 2 and Fusion-for-Godot docs, Steamworks ISteamMatchmaking, and the Among Us protocol write-up.

**Suggestions for the report:**
- Recommend promising seamless migration only for frame-insensitive games. For frame-sensitive games, fall back to the few-second pause-and-restore handover, or to ending the match gracefully with progress saved.
- Two cross-item points to reconcile: the D2 item should list Photon Fusion 2's host migration as its own pause-and-restore kind, not seamless. The GodotSteam item should check whether GodotSteam's own SteamMultiplayerPeer supports mesh connections; I found no documentation either way.

**1. How long Steam takes to transfer lobby ownership when the host crashes or pulls the cable**
- **Valve does not publish a number.** The Steamworks docs only say that "there is always one owner, and when the owner leaves another member automatically becomes owner."
- **Cable pulled:** about 30 seconds. One user reported that the other members only got the leave callback about 30 seconds after the cable was pulled (Facepunch.Steamworks issue #765, April 2024, Unity on Windows 11/macOS). This is one community report, secondhand.
- **Calling LeaveLobby normally:** the other members are notified right away through LobbyChatUpdate_t.
- **Game process crashes while the Steam client stays online:** I found no reliable figure, so this stays [不确定].
- **Steam's own connection timeout:** in Valve's open-source GameNetworkingSockets code, TimeoutInitial and TimeoutConnected both default to 10000 ms, and they can be set per connection. This is a primary source.
- **What this means:** the lobby owner transfer can only be the final fallback for agreeing who is host. It cannot be how a dead host is detected.
- **Workaround:** run your own heartbeat in the game layer, as Understudy does (170 ms of silence plus a majority vote among players). Also lower the SteamNetworkingSockets timeouts.
- I added these points to core_capabilities, quantitative_limits and key_pitfalls.

**3. Does GodotSteam's own SteamMultiplayerPeer support mesh?**
I read the source on Codeberg: the godot4 branch of the main GodotSteam repo, last committed 2026-11-05. The separate multiplayerpeer repo now says it is retired and that its code was merged into the main 4.x branch.
- **There is no `create_mesh` method.**
- **The connections are effectively a mesh.** In lobby mode (`host_with_lobby` / `connect_to_lobby`), each member connects to every other lobby member. Routing client traffic through the host is off by default (opt-in since 4.16.2), so clients send to each other directly. This differs from the expressobits version, which states it does not support mesh.
- **It still cannot migrate the host.** `create_host` always sets the host's peer ID to 1, and losing peer 1 calls `close()`, which shuts the connection down. I updated godot_integration_status and core_capabilities with this.

# Research Report - 讲述式报告（HTML）

## 触发方式
`/research-report`

## 定位（硬规则）
最终报告是主线程（Opus）把全部调研**汇聚、浓缩**之后的**讲述版**——像给客户讲解、给小孩讲故事一样有条有理，而不是把调研内容一股脑搬上来。
- **只展示**：推导/判断过程、支撑推导的核心数据、结论。
- **正文不展示**：逐句出处、来源堆砌；各 item 的字段详情、item 目录、原始字段堆砌。
- **页面最下方附"核心参考网页"**：只摆一部分高价值网页（精选，不是全量来源列表）；全量来源与明细仍留在 `results/*.json`（research 分支）备查。
- **必须记录"制作信息"**：起始问题、主模型、使用的 skill、执行模式、制作时间（写法见 Step 3）。

## 执行流程

### Step 1: 定位结果
在当前工作目录查找 `*/outline.yaml`，读取 topic、request（起始问题）、questions（用户原始问题，如有）、started_at、execution.mode、agent_groups 和 output_dir。

### Step 2: 通读与提炼（主线程 Opus）
读取 output_dir 下全部 JSON（兼容扁平/嵌套结构；跳过值里含 `[不确定]`、列在 uncertain 数组或为空的字段），提炼出：
- 回答每个核心问题所需的**关键事实与数字**：同一数字多源冲突时先调和口径，报告里只保留一个说法；
- 能串起全部问题的**主线**：从背景讲起，一步步推到结论；
- 每个判断的**理由链**：因为 A（数据）→ 所以 B → 因此 C；标明哪些是推算、哪些是主观判断；
- **核心参考网页候选**：从各 JSON 的 sources 里挑高价值网页——优先 opus 且单 item 子 agent（agent_groups 里 model 为 opus、只含一个 item 的组）的核心来源，以及一手来源（财报/业绩公告、电话会纪要、官方公告与文档、监管文件）；去重，剔除低质量转载/聚合站。

### Step 3: 写成讲述版 HTML
在 `{topic}/` 下生成 `generate_report.py`（讲述正文可放在同目录的 `build_report_content.py`；两者都不入库），产出**单文件自包含 HTML**。

**讲述结构**（按题目取舍，不必逐条照搬）：
1. **先给结论**：一句话答案 + 3–5 个核心数字（数字卡片只写数值、含义和时间口径，不写出处）。
2. **章节导航**：列出各章标题（锚点跳转），让读者一眼看到故事的脉络。
3. **按"问题 → 推导 → 数据 → 结论"逐章展开**：每章以一个问题开头，先给答案再讲理由；只放支撑这一步的数据；章与章之间要有承接（"这就引出下一个问题……"）。优先用用户的原始问题（outline 的 questions）作为章节线索。
4. **类比与图**：复杂机制用贴切的类比讲清楚；图表只画支撑推导的关键数据（遵循 dataviz 规范，配色随主题），每张图配可展开的数据表。
5. **收尾**：一页总结（几条要点）+ 接下来要盯的信号/指标。
6. **阅读说明**（可选、简短）：哪些是推算、哪些口径不完全可比；来源统一放页面最下方。
7. **制作信息**（必需，一张小卡片，放在页首结论之后或页尾参考网页之前）：
   - 起始问题：outline 的 `request`（没有就把用户最初的提示词压缩提炼成一两句）；
   - 主模型：主线程实际使用的模型——生成报告时向会话查询，不凭记忆写；只写进报告，不写进 outline.yaml 等入库文件；
   - 使用的 skill：如 `research` → `research-deep` → `research-report`，注明子 agent 类型（`web-search-agent` / `web-search-agent-deep`）及各自的模型档位；
   - 执行模式：性能 / 标准 / 经济；
   - 制作时间：`started_at` 至报告生成时间，注明时区与总用时。
8. **核心参考网页**（必需，页面最下方）：按主题分组，每条 = 标题（可点击链接，新窗口打开、`rel="noopener"`）+ 发布方/日期；约 10–25 条；正文不回引编号。

**写作要求**：浅白、有条理，每段只讲一件事；先结论后理由；数字少而精，只留能说明问题的那个；区分事实与判断（判断用"我判断""推断"等措辞）；不堆术语、不堆长串列表。

**输出与命名（硬规则）**：
- 报告一律 **HTML**，输出为**单个自包含 `.html` 文件**（CSS/JS 全部内联，无外部依赖）。
- **文件名用报告标题**：取 outline.yaml 的 `topic`（或用户指定的标题）做 slug（空格→`-`、去特殊字符），如 `谷歌护城河与长坡厚雪.html`。不要用 `report.html` 这种通用名。
- 综合与研判由**主线程 Opus**完成（`research-report` 阶段始终 Opus，见 CLAUDE.md）。

**HTML 硬规则**：
- **白天/深色两种背景模式**：页面内置一个切换按钮（右上角），同时跟随系统 `prefers-color-scheme`；用 CSS 变量定义两套配色（`:root` 亮色 + `[data-theme="dark"]`/媒体查询暗色），`body` 显式设背景色。切换状态可用 `localStorage` 记住（try/catch 包裹）。
- 响应式：手机宽度（~400px）可读，左右留 ≥16px 边距，页面无横向滚动（宽表格、图表在自身容器内横向滚动）。
- 可读性：清晰的排版层级；表格和坐标轴的数字用 tabular-nums；图表用内联 SVG。

### Step 4: 执行并交付
1. 运行 `python {topic}/generate_report.py` 生成 `{标题slug}.html`，截图检查白天、深色和手机宽度下的版面。
2. **交付方式（硬规则）**：**直接给用户一键可下载的文件**——用 `SendUserFile`（`display="attach"` 下载卡）把该 HTML 交付。**不要用 Artifact / 网页部署功能发布。** 本地 CLI 环境下文件已在 `{topic}/` 目录，告知路径、用户直接打开即可。

## 输出
- `{topic}/generate_report.py`（及可选的 `build_report_content.py`）- 渲染脚本与讲述正文（可再生物，不入库）
- `{topic}/{标题slug}.html` - 讲述式报告（HTML，含白天/深色切换；可再生物，不入库）
